# 자가 점검 과제 (Practice Quests)

> 목적: nextstep-claude-os를 만들며 쓴 기술을 **직접 다시 만들어보며** 응용력을 높이고 까먹지 않기.
> 사용법: 각 과제는 **정답을 보기 전에 먼저 떠올려 만든다 → 막히면 "참고" 파일을 연다 → 동작 확인.**
> 난이도: ★ 재현(기억 인출) · ★★ 변형(응용) · ★★★ 통합(설계)

---

## 규칙 (학습 효과를 위한 약속)

1. **먼저 빈손으로** — 각 영역 맨 위 "💭 먼저 떠올리기" 질문에 *파일을 열지 않고* 답해본다.
2. **막히면 그때 연다** — 기존 코드를 처음부터 베끼지 않는다. 30초 막히면 참고 파일을 본다.
3. **동작으로 확인** — "확인 포인트"가 실제로 충족되는지 눈으로 본다. 머릿속 "될 것 같다"는 통과 아님.
4. **변형까지 가야 내 것** — ★를 재현했으면 반드시 ★★ 변형을 시도한다. 재현만으론 안 남는다.

---

## 영역 1 — 스킬 (Slash Command)

💭 **먼저 떠올리기**: 스킬 파일에서 사용자 입력은 어떤 키워드로 받지? 스킬과 에이전트의 역할 경계는?

### 1-① ★ `/today` 스킬 만들기
- **만들 것**: `.claude/commands/today.md` — 오늘 날짜와 `current.md`의 현재 `status`를 한 줄로 출력.
- **확인 포인트**: `/today` 호출 시 `2026-06-11 | status: structured` 형태 출력.
- **참고**: `.claude/commands/status.md`

### 1-② ★★ 인자를 받는 `/note` 스킬
- **만들 것**: `/note <텍스트>` → `current.md`의 `## 다음 행동` 섹션에 한 줄 추가하는 스킬.
- **확인 포인트**: `$ARGUMENTS`로 입력을 받고, 입력이 없으면 사용법 안내 후 종료(게이트키퍼 패턴).
- **참고**: `.claude/commands/task.md` (입력 검증 → 처리 흐름)

### 1-③ ★★ 스킬은 얇게, 로직은 에이전트로
- **만들 것**: 1-②의 `/note`를 "검증만 하는 스킬 + 실제 기록하는 `note-agent`"로 분리.
- **확인 포인트**: 스킬 본문에는 입력 검증·위임만 남고, 파일 수정 로직은 에이전트에 있다.
- **참고**: `ask.md` ↔ `ask-agent.md` 쌍

## 영역 2 — 서브 에이전트

💭 **먼저 떠올리기**: 에이전트 frontmatter의 필수 3요소는? `tools:`를 좁히면 뭐가 좋아지지?

### 2-① ★ 최소 에이전트 재현
- **만들 것**: `summary-agent` — `current.md`를 읽고 3줄 요약을 반환. frontmatter(`name`/`description`/`tools`) 포함.
- **확인 포인트**: `tools:`에 `Read`만 넣어도 동작한다(쓰기 권한 없이).
- **참고**: `.claude/agents/record-agent.md`

### 2-② ★★ 도구 최소권한 실험
- **해볼 것**: `summary-agent`에 `Write`를 추가했을 때와 뺐을 때 무엇이 달라지는지 직접 확인하고, 왜 최소권한이 안전한지 한 줄로 적기.
- **확인 포인트**: "이 에이전트는 왜 이 도구만 필요한가"를 description에 근거로 녹였다.

## 영역 3 — 멀티 에이전트 오케스트레이션

💭 **먼저 떠올리기**: 서브 에이전트끼리는 어떻게 데이터를 주고받지? 왜 직접 대화하지 않지?

### 3-① ★★ 2단계 미니 파이프라인
- **만들 것**: `draft-agent`(초안 작성) → `polish-agent`(다듬기) 2단계를, 작은 오케스트레이터 스킬 `/write <주제>`로 순서 호출.
- **확인 포인트**: 두 에이전트가 **공유 파일 하나**(예: `/tmp/draft.md`)를 읽고/쓰며 바통을 넘긴다. status 같은 진행 표시를 둔다.
- **참고**: `os-orchestrator.md`(호출 순서·current.md 통신), `orchestrator-evolution.md`(원칙 2)

### 3-② ★★★ 분기 있는 오케스트레이션
- **설계할 것**: 입력 길이에 따라 `polish-agent`를 건너뛰는 분기를 오케스트레이터에 추가. "조율자는 일하지 않는다" 원칙을 지키면서 분기 판단만 조율자가 하도록 설계.
- **확인 포인트**: 분기 로직이 조율자에 있고, 실제 작업은 여전히 에이전트가 한다.

## 영역 4 — 훅 (Hooks)

💭 **먼저 떠올리기**: 훅은 stdin으로 무엇을 받지? `UserPromptSubmit`과 `Stop`의 차이는?

### 4-① ★ 입력 들여다보기
- **만들 것**: `UserPromptSubmit` 훅 스크립트 하나 — 들어온 JSON에서 `prompt`를 꺼내 `/tmp/last_prompt.txt`에 저장.
- **확인 포인트**: 아무 프롬프트나 보낸 뒤 파일에 내용이 남는다.
- **참고**: `.claude/hooks/skill-start.sh` (stdin JSON 파싱 패턴)

### 4-② ★★ 시작-종료 짝 맞추기
- **해볼 것**: `skill-start.sh`/`skill-stop.sh`가 `/tmp` 임시파일로 어떻게 시작·종료를 잇는지 읽고, "강제 종료 시 로그가 유실되는 이유"를 한 줄로 설명.
- **확인 포인트**: `os-analysis.md` D-3/B-3 항목과 내 설명이 일치하는지 대조.
- **참고**: `os-analysis.md` (훅 분석 절)

### 4-③ ★★ settings.json 연결
- **확인할 것**: 훅 등록 시 경로를 **절대경로**로 쓰는 이유를 직접 상대경로로 바꿔보고 깨지는지 확인(실험 후 원복).
- **참고**: `settings.json`, `os-analysis.md` D-1

## 영역 5 — 공통화 & 컨텍스트 주입

💭 **먼저 떠올리기**: 같은 파싱 코드가 두 스킬에 있으면 왜 위험하지? 에이전트는 사용자 취향을 어디서 읽지?

### 5-① ★ lib 추출
- **만들 것**: 아무 스킬 둘이 공유할 수 있는 작은 파이썬 함수를 `.claude/lib/`에 두고 양쪽에서 호출.
- **확인 포인트**: 로직을 한 곳만 고치면 양쪽이 같이 바뀐다.
- **참고**: `.claude/lib/skill_stat_parser.py`, `skill-stat.md`·`slack-stat.md`

### 5-② ★★ 컨텍스트 주입
- **해볼 것**: 2-①의 `summary-agent`가 작업 전에 `profile.md`를 읽고 "요약 톤을 사용자 레벨에 맞춘다"는 한 줄을 출력하도록 추가.
- **확인 포인트**: 에이전트 절차 0단계에 컨텍스트 로드가 있고, 출력에 반영된다.
- **참고**: `interpret-agent.md`(0단계 profile 로드), `implement-agent.md`(0단계 craft 로드)

## 영역 6 — 통합 챌린지 (졸업 과제)

💭 이 과제 하나로 위 6영역이 다 들어간다. 막힐 때만 참고를 열고, 끝나면 직접 회고를 적는다.

### 6-① ★★★ 미니 워크플로우 "한 입 크기"로 새로 만들기
- **만들 것**: `/digest <URL이나 주제>` — 다음을 잇는 **2~3단계 파이프라인**:
  1. 스킬: 입력 검증(게이트키퍼)
  2. 오케스트레이터/조율: 순서 호출
  3. 에이전트 A: 자료 해석 → 공유 파일에 기록
  4. 에이전트 B: 핵심 3줄 + 다음 행동 1개로 정리
  5. (선택) 훅: 호출 시각 로깅
- **확인 포인트(스스로 체크리스트)**:
  - [ ] 스킬은 검증·위임만 한다 (로직 없음)
  - [ ] 에이전트는 공유 파일로만 통신한다
  - [ ] 각 에이전트 `tools:`가 최소권한이다
  - [ ] 조율자는 직접 일하지 않고 분기/순서만 본다
  - [ ] 공통 로직이 있으면 lib로 뺐다
- **회고로 마무리**: "재현 vs 변형 vs 설계 중 어디서 가장 막혔나?" 한 단락 적기.
