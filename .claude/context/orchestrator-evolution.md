# 오케스트레이터 구조 진화: As-Is → To-Be

> 작성일: 2026-06-11
> 주제: 단일 에이전트 기반 → 전문 서브 에이전트 위임 구조로의 전환
> 관련 커밋: `145c0f3`(스킬-에이전트 분리), `cf59a9a`(curate-agent 분리)

---

## 0. 한 줄 요약

**"혼자 다 하는 팀장" → "각 전문가에게 위임하고 흐름만 챙기는 팀장".**
오케스트레이터는 *조율만* 하고, 실제 작업(해석·구조화·구현·기록·정리)은 전부 전문 서브 에이전트가 맡는다.

---

## 1. 전체 파이프라인 (현재 = To-Be)

```
사용자
  │  /task "요구사항"
  ▼
┌─────────────────────────────────────────────────────────┐
│  task.md (스킬)                                          │
│  · 요구사항 유무 / 진행 중 작업(status) 검사 = 게이트키퍼  │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  os-orchestrator (조율자)                                │
│  · profile.md / craft.md 로드                            │
│  · current.md 초기화 (에이전트 간 유일한 통신 수단)       │
│  · 5단계를 순서대로 호출만 함                            │
└───┬───────┬───────┬───────┬───────┬─────────────────────┘
    ▼       ▼       ▼       ▼       ▼
  ① interpret  ② structure  ③ implement  ④ record  ⑤ curate
   해석         구조화        구현          기록       전파
    │           │            │             │          │
    └───────────┴── current.md 에 읽고/쓰며 이어달리기 ──┘
                                                       │
                                                       ▼
                                          history.md / craft.md / profile.md
```

각 단계는 `current.md`의 `status`를 바꾸며 바통을 넘긴다:
`new → interpreted → structured → implemented → done`

---

## 2. As-Is — 단일 에이전트 + 오케스트레이터가 정리까지 직접

```
os-orchestrator
  ├─ ① interpret-agent 호출
  ├─ ② structure-agent 호출
  ├─ ③ implement-agent 호출
  ├─ ④ record-agent 호출
  └─ ⑤ [오케스트레이터가 직접 수행]   ◀── 문제 지점
        · history.md 기록
        · craft.md / profile.md 갱신 판단
        · 사용자 보고
```

스킬도 로직을 직접 들고 있었다:

```
ask.md (스킬)
  └─ 질문 처리 로직 + 답변 생성을 스킬 본문이 직접 담당
```

**문제점**
- 오케스트레이터 본문에 세션 정리 로직이 인라인 → 단계가 늘수록 본문 비대화, 책임 혼재
- `record`(자산 추출)와 정리(영구 전파)가 한 컴포넌트에 뭉쳐 있어 경계가 흐림
- 스킬이 로직까지 떠안아 진입점/실행자 구분 없음

---

## 3. To-Be — 전 단계 위임 + 정리도 별도 에이전트

```
os-orchestrator           ◀── "조율과 사용자 출력에만 집중"
  ├─ ① interpret-agent
  ├─ ② structure-agent
  ├─ ③ implement-agent
  ├─ ④ record-agent
  └─ ⑤ curate-agent       ◀── 신규 분리: 세션 정리 전담
        · history.md 기록
        · craft.md / profile.md 갱신 판단
```

스킬은 얇은 게이트키퍼로 분리:

```
ask.md (스킬)             ◀── 22줄 → 12줄로 축소
  └─ 입력 검증만 하고 → ask-agent 에 위임
```

---

## 4. 무엇이 / 왜 바뀌었나

| 구분 | As-Is | To-Be | 이유 |
|------|-------|-------|------|
| **세션 정리** | 오케스트레이터 본문에 인라인 | `curate-agent` 분리 | record(자산 추출)와 curate(영구 전파)는 다른 책임. record와 대칭되는 5단계로 경계 명확화 |
| **스킬 역할** | 스킬이 로직까지 수행 | 스킬은 검증·위임, 로직은 에이전트 | 스킬 = 진입점/게이트키퍼, 에이전트 = 실행자 |
| **오케스트레이터** | 조율 + 실무 | 조율 전용 | 한 컴포넌트가 한 가지만 책임 (단일 책임) |
| **컨텍스트 비용** | 긴 본문 = 매번 토큰 소모 | 위임으로 본문 축소 | 서브 에이전트는 독립 컨텍스트 실행 → 메인 대화 컨텍스트 절약 |

---

## 5. 핵심 설계 원칙 2가지

### 원칙 1 — "조율자는 일하지 않는다"

오케스트레이터가 직접 파일을 만지기 시작하면 단계가 늘어날수록 본문이 비대해지고 책임이 뒤섞인다.
To-Be에서는 *"누구를 언제 부를지"*만 알고, 실제 작업은 모두 위임한다.
(단, `current.md` 초기화처럼 조율에 필요한 최소 작업은 직접 한다.)

### 원칙 2 — "current.md = 단일 통신 채널"

서브 에이전트들은 서로 직접 대화하지 않는다. 각자 독립 컨텍스트에서 실행되므로,
`current.md` 파일 하나를 읽고/쓰며 바통을 넘긴다.
이것이 서브 에이전트 구조가 성립하는 핵심 메커니즘이다 — 에이전트가 늘어나도 통신 구조는 그대로다.

## 6. 에이전트 역할 요약

| 단계 | 에이전트 | 입력 (current.md) | 출력 섹션 | status 전이 |
|------|----------|-------------------|-----------|-------------|
| ① | interpret-agent | 원본 요구사항 | 해석 결과 | → interpreted |
| ② | structure-agent | 해석 결과 | 구조화 결과 | → structured |
| ③ | implement-agent | 구조화 결과 | 구현 결과 | → implemented |
| ④ | record-agent | 작업 전체 | 재사용 자산 | → done |
| ⑤ | curate-agent | 재사용 자산 | (history/craft/profile로 전파) | (영구 지식화) |
